# Does a lever cost quality? The A/B suite

[← README](../README.md)

Everything context-doctor removes is supposed to be waste. `ab` checks that on tasks with a right answer: each task of a small suite runs twice, with and without a lever, through the Anthropic Messages API, and is scored by its own test. A smaller context only counts if the task still passes.

```bash
export ANTHROPIC_API_KEY=sk-ant-...
context-doctor ab                      # the plan and the estimated cost; nothing is sent
context-doctor ab --yes                # run it
context-doctor ab --lever autoclear --repeat 3 --yes --out ab.json
```

## The tasks

Eight small coding tasks (`context-doctor ab --list`), each a tiny JavaScript repository written into a temporary folder, a request, and a check (`node test.mjs`, exit 0 = pass):

| Task | What it asks |
|---|---|
| `range-inclusive` | an off-by-one and two edge cases |
| `slugify` | a function from a five-rule spec |
| `ini-parser` | a parser from one section of a long format document (~8k tokens) |
| `retry-backoff` | a bug the production log (~10k tokens) points at |
| `csv-quotes` | quoted fields in a CSV parser |
| `rename-export` | a rename across three files, keeping a deprecated alias |
| `ttl-cache` | a small class from a design doc (~3k tokens) |
| `money-format` | currency formatting edge cases |

The three big files are where the levers act; on the five small tasks a lever should change nothing, which is a result too. Everything is generated by the package: no network, no dependencies, nothing from anyone's sessions. The test suite checks that every fixture fails its check and passes with a reference fix the agent never sees.

## The agent

A minimal tool loop, the same in every arm: `read_file`, `write_file` (whole files; `test.mjs` cannot be written) and `run_check`, with a short system prompt, top-level automatic prompt caching, and up to 16 requests a run (`--max-turns`). When the agent stops, the harness restores `test.mjs` and runs it: the check decides, not the model's last message.

## The levers

| Lever | Compared with | What the arm does |
|---|---|---|
| `rules` | `none` | the five standing context rules in the system prompt, verbatim: what MCP clients and the GitHub Copilot hook inject. They name the MCP tools (`profile_context`, `pack_context`), which this arm does not offer, so a call to one gets "no such tool": the arm measures the text alone |
| `autoclear` | `none` | the client is wrapped with `withContextDoctor` (autopilot in process), and every request is treated as coming after an idle gap, so stale tool output is cleared whenever a batch is big enough (1 result kept, batches from 1,000 tokens). Shipped autopilot clears far less (cold cache only, 3 kept, 20,000-token batches): this is the worst case for quality, and its cost is not autopilot's cost |
| `pack` | `none` | a `pack_context` tool (the same chunking and ranking as `context-doctor pack`, 1,500-token budget) and the rule to use it for big files instead of reading them whole |
| `compact` | `compact-generic` | both arms compact once, after the second request; `compact` adds the PreCompact hook's instructions (files changed, failing checks, the user's own instructions), built from the run's history the way the hook builds them from a Claude Code transcript |

`none` is shared by `rules`, `autoclear` and `pack`, so `--lever all` runs six arms per task.

## Output

A table per lever: each task's pass (or passes out of `--repeat`), billed tokens per run (prompt including cache reads and writes, plus output) and cost, then pass counts, the token and cost change, and what the lever did (requests autopilot changed and the tokens it kept off the wire, `pack_context` calls, compactions). Runs that ended on an API error or refusal, the budget, or a turn or token cap are counted apart: they say nothing about the lever. `--json` prints every run; `--out file` writes it as well. Progress goes to stderr.

With one run per task, a one-task difference is noise. Use `--repeat 3` or more before quoting a number.

## Spending

`ab` is the only command besides `experiment` that spends money, and it bills the key in `ANTHROPIC_API_KEY`:

- it always prints the plan and an estimate first (with prompt caching, and the upper end if nothing caches), and refuses to start without the key;
- without `--yes` it sends nothing;
- it stops starting requests once `--budget` USD is spent (default: the upper estimate plus 25%, at least $1);
- `--model` picks the model (default `claude-opus-5-5`; a model without a price in the table is refused, since the cap needs one). `--concurrency` sets runs in flight (default 4).

`ANTHROPIC_BASE_URL` is honoured and printed, so a proxy in the way (autopilot's included) is visible: point it at the API itself for a clean baseline.

On accounts that enforce thinking-block binding (created on or after 2026-08-31), an edited history before a thinking block is refused; the wrapper then resends the request unedited, as in production, and the `autoclear` row shows how many requests it actually changed.

## In code

The provider is an interface, so the suite can run anywhere that answers a Messages API request:

```ts
import { runAbSuite, renderAb, anthropicProvider, AB_TASKS } from "context-doctor";

const result = await runAbSuite({
  provider: anthropicProvider({ apiKey: process.env.ANTHROPIC_API_KEY! }), // or { name, create(body) { ... } }
  model: "claude-sonnet-5-5",
  levers: ["autoclear"],
  repeat: 3,
  budgetUsd: 5,
});
console.log(renderAb(result));
```

The package's own tests run the whole harness through the CLI against a local mock of the Messages API whose scripted model solves each task the same way every time: every arm, each lever acting, the check deciding, the budget and the consent gates.
