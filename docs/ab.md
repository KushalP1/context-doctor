# Does a lever cost quality? The A/B suite

[← README](../README.md)

Everything context-doctor removes is supposed to be waste. `ab` checks that on tasks with a right answer: each task of a small suite runs twice, with and without a lever, through the Anthropic Messages API, and is scored by a hidden check. A smaller context only counts if the task still passes.

```bash
export ANTHROPIC_API_KEY=sk-ant-...
context-doctor ab                      # the plan and the estimated cost; nothing is sent
context-doctor ab --yes                # run it
context-doctor ab --lever autoclear --repeat 3 --yes --out ab.json
```

## The tasks

Eight small coding tasks (`context-doctor ab --list`), each a tiny JavaScript repository written into a temporary folder, a request, a smoke test the agent can run, and a hidden check it cannot see:

| Task | What it asks | Where the facts are |
|---|---|---|
| `range-inclusive` | an off-by-one and two edge cases | the request |
| `slugify` | a function from a five-rule spec | a short README |
| `ini-parser` | a parser for a config format | section 7 of a long format document (~8k tokens), with the older version's rules as a decoy in section 5 |
| `retry-backoff` | a bug in a retry helper | the retry policy, logged once in the middle of a production log (~10k tokens) |
| `csv-quotes` | quoted fields in a CSV parser | the request |
| `rename-export` | a rename across three files, keeping a deprecated alias | the request |
| `ttl-cache` | a small class | a design doc (~3k tokens), with a rejected alternative as a decoy |
| `money-format` | currency formatting edge cases | the request |

The three big files are where the levers act: there the facts the fix needs are in the big file and nowhere else, so an arm that loses them (cleared, packed badly, summarized away) fails. On the five small tasks a lever should change nothing, which is a result too. Everything is generated by the package: no network, no dependencies, nothing from anyone's sessions.

The smoke test (`node test.mjs`, the agent's `run_check`) only shows that the code loads and runs; it holds no expected values, so the answers cannot come from a failing assertion. The verdict is the hidden check, which the harness writes outside the repository and runs after the agent stops; it must run to the end and print a line with a fresh random value, so an exit code alone does not pass. The package's tests check that every fixture fails the hidden check and passes it with a reference fix the agent never sees, that the smoke test passes with the fix, and that the big-file tasks' facts appear only in their big file.

## The agent

A minimal tool loop, the same in every arm: `read_file`, `write_file` (whole files; `test.mjs` cannot be written; no path outside the repository or through a symbolic link) and `run_check`, with a short system prompt, top-level automatic prompt caching, and up to 16 requests a run (`--max-turns`, the compaction's included).

The agent's code runs twice over (its smoke tests, then the hidden check), so it runs contained: with only `PATH` and a throwaway `HOME` in its environment (no API key), in its own process group, killed after 30 seconds, and with anything it left running killed when the run ends (by process group, then by working directory through `/proc` or `lsof`). Whatever stands at `test.mjs` before a smoke run (an edited file, a folder, a link to anywhere) is removed without being followed and the shipped file written anew. Each run's folder is removed at the end even if the code locked it read-only, and Ctrl-C removes them all and exits 130. It is a quality test, not a sandbox: the code runs as you.

## The levers

| Lever | Compared with | What the arm does |
|---|---|---|
| `rules` | `none` | the five standing context rules in the system prompt, verbatim: what MCP clients and the GitHub Copilot hook inject. They name the MCP tools (`profile_context`, `pack_context`), which this arm does not offer, so a call to one gets "no such tool": the arm measures the text alone |
| `autoclear` | `none` | the client is wrapped with `withContextDoctor` (autopilot in process), and every request is treated as coming after an idle gap, so stale tool output is cleared whenever a batch is big enough (1 result kept, batches from 1,000 tokens). Shipped autopilot clears far less (cold cache only, 3 kept, 20,000-token batches): this is the worst case for quality, and its cost is not autopilot's cost |
| `pack` | `none` | a `pack_context` tool (the same chunking and ranking as `context-doctor pack`, 1,500-token budget) and the rule to use it for big files instead of reading them whole |
| `compact` | `compact-generic` | both arms compact once, after the second request, and go on from the summary alone (the request is not repeated: what the summary dropped is gone); `compact` adds the PreCompact hook's instructions (files changed, failing checks, the user's own instructions), built from the run's history the way the hook builds them from a Claude Code transcript |

`none` is shared by `rules`, `autoclear` and `pack`, so `--lever all` runs six arms per task.

## Output

A table per lever: each task's pass (or passes out of `--repeat`), billed tokens per run (prompt including cache reads and writes, plus output) and cost, then pass counts over the runs that completed, the token and cost change, and what the lever did (requests autopilot changed and the tokens it kept off the wire, `pack_context` calls, compactions). Runs that ended on an API error or refusal, the budget, or a turn or token cap are counted apart and left out of the pass counts: they say nothing about the lever. When the two arms completed different numbers of runs, the verdict compares pass rates. `--json` prints every run; `--out file` writes it as well (checked before anything is sent). Progress goes to stderr.

The exit code is 1 when the API refused the key (the suite stops at the first refusal, 401 or 403) or when every run of an arm ended on an API error; failed tasks are results, not errors.

With one run per task, a one-task difference is noise. Use `--repeat 3` or more before quoting a number.

## Spending

`ab` is the only command besides `experiment` that spends money, and it bills the key in `ANTHROPIC_API_KEY`:

- it always prints the plan and an estimate first (with prompt caching, and the upper end if nothing caches), and refuses to start without the key;
- without `--yes` it sends nothing;
- `--budget` USD (default: the upper estimate plus 25%, at least $1) is never passed: before each request its worst case (the whole prompt as cache writes, plus 16,000 output tokens) is held against the budget until it answers, so runs in flight cannot overshoot it together;
- `--model` picks the model (default `claude-opus-5-5`); it needs a price row for that model itself, since the cap depends on it, so an id the price table only knows by family is refused. `--concurrency` sets runs in flight (default 4);
- a 429, a 5xx, a 529, a connection that fails or a body cut short is retried with backoff (honouring `retry-after`).

`ANTHROPIC_BASE_URL` is honoured and printed, so a proxy in the way (autopilot's included) is visible: point it at the API itself for a clean baseline.

On accounts that enforce thinking-block binding (created on or after 2026-08-31), an edited history before a thinking block is refused; the wrapper then resends the request unedited, as in production, and the `autoclear` row shows how many requests it actually changed.

## In code

The provider is an interface, so the suite can run anywhere that answers a Messages API request:

```ts
import { runAbSuite, renderAb, anthropicProvider, AB_TASKS } from "context-doctor";

const result = await runAbSuite({
  provider: anthropicProvider({ apiKey: process.env.ANTHROPIC_API_KEY! }), // or { name, create(body) { ... } }
  model: "claude-sonnet-5-5",
  levers: ["autoclear"],
  repeat: 3,
  budgetUsd: 5,
});
console.log(renderAb(result));
```

The package's own tests run the whole harness through the CLI against a local mock of the Messages API whose scripted model solves each task the same way every time: every arm, each lever acting, the hidden check deciding, the consent and budget gates, a refused key, a body cut short, and the agent's code trying to read the key, outlive its run, write through a link, lock its folder or loop forever.
